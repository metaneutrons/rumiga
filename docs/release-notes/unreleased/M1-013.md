# M1-013: Selectable Video Standard

- Status: Unreleased
- Change type: Added
- Task: M1-013
- Audience: Users, embedded integrators, and maintainers

## Summary

`--ntsc` now selects an NTSC machine. The video standard fixes the frame length, the
colour clock, the active height, the beam wrap, and what `VPOSR` and `BEAMCON0` report,
so the guest detects the standard and adapts its display window.

## User And Operator Impact

`--ntsc` previously changed nothing. It printed a warning and produced output
byte-identical to PAL, so the option offered a choice the machine could not make.

An NTSC machine now runs 262 scanlines at 3 579 545 Hz, a frame period of 16.615 ms
implying 60.19 Hz, and an active height of 243 lines. PAL remains 312 lines at
3 546 895 Hz, 19.968 ms and 288 lines, and is still the default.

The same Kickstart ROM boots both standards. There is no separate NTSC ROM, because
the standard is reported by the chipset rather than compiled into the ROM.

The guest acts on it. Under `--ntsc`, Kickstart 46.143 sets a display window from line
21 to line 262, against PAL's line 29 to line 312. The two stop lines are exactly the
two standards' line counts, so the guest derived them from the standard it read.

The startup summary reports the standard with its line count, frame rate, and active
height instead of a bare label and a warning.

## Compatibility And Migration

`MemoryConfig` gains a `video_standard` field. Code that constructs the struct
literally must add it; every model profile defaults to PAL, so
`MemoryConfig::a500()` and its siblings need no change.

`CustomChipState::new` takes the video standard. `CustomChipState::default()` is PAL.

`Emulator::frame_period` now depends on the standard. A shell that paces against it, as
ADR-0011 requires, follows the standard automatically. `Emulator::active_height` is new
and a presenter should crop to it: the framebuffer stays PAL-sized in both standards, so
using the buffer height would append 45 never-written lines to an NTSC frame.

`Emulator::state_digest` includes the standard, so recorded digests from before this
change no longer compare. Frame digests are unaffected.

`CustomChipState::read_register(VPOSR)` now includes the `LOF` bit. It previously had
its own implementation that omitted it while the register shadow the guest reads
included it; the two are now one implementation. The guest-visible value did not change,
because guest reads go through the shadow and this direct read is currently exercised
only by tests.

Capture manifests keep `video_standard` as a plain string and gain a `video_timing`
object with the line count, colour clock, frame period, and active height. The
`native_framebuffer` section gains `active_height` alongside the unchanged buffer
`height`.

## Verification

Every constant is pinned in both runtime profiles against the values `WinUAE` records,
including the two that are the same in both standards, so a future change cannot make
the line length or the buffer maximum standard-dependent by accident.

One test asserts that the beam wrap agrees with the frame length. It fails on an
implementation that shortens the frame without moving the wrap, reporting the beam at
line 262 rather than back at the top of the frame.

On the host, three consecutive 1200-frame NTSC captures of Kickstart 46.143 are
byte-identical to each other, and the recorded manifest shows the guest's display
window following the standard.

PAL output is unchanged. A 1200-frame A1200 capture is byte-identical to the same
capture taken from the pre-change revision, and the 60-frame capture keeps the digest
recorded for M1-005 and M1-006.

Pull-request run `32127572185` and final `main` run `32128162254` passed all required

## Known Limitations

The Agnus revision is not modelled. `VPOSR` reports revision `0x00`, which is OCS, on
every model profile; only the standard bit varies. A guest that identifies ECS or AGA
Agnus by its revision field sees what it saw before.

Interlace and long/short frame alternation are not modelled. `LOF` is always set, and
NTSC's half-line is ignored: a frame is a flat 262 lines rather than alternating 262
and 263.

The standard is fixed at construction. Writing `BEAMCON0` from the guest does not switch
it at runtime.

Nothing is compared against a reference emulator yet. The constants come from `WinUAE`
sources and the guest behaviour is self-consistent, but no frame has been diffed
against `WinUAE` or FS-UAE output.
