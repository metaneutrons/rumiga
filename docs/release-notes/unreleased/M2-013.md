# M2-013: Product Flash Partition Layout

- Status: Unreleased
- Change type: Added
- Task: M2-013
- Audience: Firmware integrators and maintainers

## Summary

The repository now owns the D1001 flash layout in `firmware/partitions.csv`. It
replaces the stock ESP-IDF single-application table with two 6 MiB OTA slots, a
crash-dump partition, a `storage` partition, and a bootloader window large enough
for a signed bootloader.

## User And Operator Impact

The flashable image gains update, rollback, crash-dump, and device-side storage
capability. `nvs` grows from 24 KiB to 320 KiB so configuration and Wi-Fi
credentials have room to grow, and `nvs_keys` is reserved so NVS encryption can be
enabled later without moving anything.

`CONFIG_PARTITION_TABLE_OFFSET` moves from `0x8000` to `0x10000`. The old offset
left the 24,096-byte bootloader 480 bytes of headroom, which cannot hold a Secure
Boot V2 signature block.

## Compatibility And Migration

This changes where everything lives in flash, so a device flashed with an earlier
image must be reflashed over cable rather than updated. That is a one-time cost
because no device has been flashed yet.

Both application slots sit at fixed offsets with the variable-size data partition
last. Qualifying the board's full 32 MB part therefore extends `storage` from
3.5 MiB to 19.5 MiB and does not invalidate an image built against the 16 MB
table.

Secure Boot is reserved, not enabled. Building signed binaries requires a private
key that must not enter the repository or the evidence bundle; offline signing
against a protected key belongs to the release process.

## Verification

The evidence task verifies that the merged image embeds the layout declared by
`firmware/partitions.csv` entry by entry, that the bootloader fits its 57,344-byte
window, and that the application fits its slot. The build manifest records the
decoded layout, so a change is visible in the manifest diff. A unit test asserts
that the shipped layout is contiguous, 4 KiB aligned with 64 KiB aligned
application slots, fills the configured geometry exactly, and declares two
equal-sized slots.

Slot sizing rests on a measured forecast rather than a guess. A bare-metal RISC-V
probe that forces full instantiation of the emulator measures 540 KiB of code and
read-only data for `rumiga-core`, `m68k`, and `rumiga-platform`; a
feature-complete image is forecast between 1.8 MiB and 3.8 MiB.

## Verified Promotion

Pull-request run `32046813352` and final `main` run `32047348837` passed all
required jobs. Both governance artifacts were independently checksum verified, and
the eight partitions decoded straight out of the hosted flashable image match
`firmware/partitions.csv` entry by entry.

## Known Limitations

Nothing has been flashed or booted. The 57,344-byte bootloader window is a
reasoned choice, not a measurement against an actually signed bootloader, which is
why the gate now asserts the window rather than assuming it.

`storage` is declared as FAT, whose metadata is not crash consistent. The
partition is reserved for device-side data such as Kickstart images the owner
uploads; the firmware never ships those. Emulator media stays on the MicroSD under
the bounded block-device contract.
