# M1-002: Portable Stock CPU Profiles

- Status: Unreleased
- Change type: Changed
- Task: M1-002
- Audience: Embedded integrators and maintainers

## Summary

The active `m68k` CPU crate now supports explicit `std` and allocator-backed
`no_std` profiles. The stock M68000 and 68EC020-class path, together with the
complete `rumiga-core` dependency graph, compiles as an optimized release build
for bare-metal 32-bit RISC-V.

## User And Operator Impact

Default desktop behavior is unchanged and retains the existing FPU
implementation. Embedded integrations select
`--no-default-features --features no_std` for both CPU and core and must provide
a global allocator when linking the final firmware.

## Compatibility And Migration

The `m68k` dependency now requires exactly one runtime profile when default
features are disabled. Its `fpu` feature requires `std`; unsupported FPU
opcodes in the stock profile continue through the existing Line-F path.
Workspace consumers should forward runtime features explicitly rather than
relying on Cargo feature unification.

## Verification

The canonical host gate checks the `m68k` feature matrix, strict Clippy, the
FPU-less Line-F regression, the full default workspace, and `rumiga-core` under
both runtime profiles. The portable gate builds the foundational packages and
then `m68k` plus `rumiga-core` with `no_std` in release mode for
`riscv32imafc-unknown-none-elf`.

## Known Limitations

This is compile-time bare-metal evidence, not D1001 execution or performance
evidence. Portable FPU math is intentionally excluded. Injected trace services
and deterministic single-owner blitter execution remain M1-004 and M1-005.
