# M2-014: Reversible Security Posture

- Status: Unreleased
- Change type: Added
- Task: M2-014
- Audience: Firmware integrators and maintainers

## Summary

Flash encryption is now enabled in Development mode with virtual eFuses, so the
configuration is exercised without any board becoming permanently different. The
firmware gate rejects every configuration that could burn an eFuse.

## User And Operator Impact

No device is altered by building or flashing this firmware. Virtual eFuses make
every eFuse operation a simulation, and release-mode flash encryption is
unselectable while they are on.

The guarantee is enforced rather than documented. The gate fails on flash
encryption or Secure Boot without virtual eFuses, on release-mode flash
encryption, and on NVS encryption through the HMAC scheme, which would consume an
eFuse key block. Turning any of it on for real requires a review-visible change to
the gate.

The build manifest gains a `reversibility` section and the `no-efuse-burn` and
`encryption-not-enforced` exclusions, so a simulated posture cannot be mistaken
for an enforced one.

## Compatibility And Migration

Nothing in flash moves. NVS encryption uses the `nvs_keys` partition the layout
already reserved, so no partition changes.

Anyone who wants real encryption on hardware must remove `CONFIG_EFUSE_VIRTUAL`
and accept that the first boot burns a key. That step is irreversible and is
deliberately outside this change.

## Verification

Measured bootloader growth: 24,096 bytes without flash encryption, 34,800 bytes
with it, and 45,056 bytes with Secure Boot V2 additionally enabled and built
unsigned. The window is 57,344 bytes, so 22,544 bytes remain free today and
roughly 8 KiB would remain with Secure Boot and its 4 KiB signature block.

This also settles an open question from the previous change. The `0x8000` table
offset used before the product layout gave a 24,576-byte window, so flash
encryption alone would not have fit. Moving the table was already necessary, not
merely prudent.

Unit tests cover the accepted posture, an absent posture, and each rejected
configuration.

## Verified Promotion

Pull-request run `32049854368` and final `main` run `32065256994` passed all
required jobs. Both governance artifacts were independently checksum verified, and
the hosted firmware bundle confirms `efuse_virtual: true`, `burns_efuses: false`,
and the absence of `CONFIG_SECURE_BOOT`.

## Known Limitations

With virtual eFuses the encryption is simulated, so this change makes no claim
about the confidentiality of flash contents. Secure Boot remains disabled, because
signed binaries require a private key that must not enter the repository or the
evidence bundle.

The HMAC scheme for NVS keys has a real security advantage over the
flash-encryption scheme and is Espressif's default on capable SoCs. Choosing it
costs one eFuse key block and belongs to the security review before manufacturing.
