# M1-010: Allocation Instrumentation

- Status: Unreleased
- Change type: Fixed
- Task: M1-010
- Audience: Embedded integrators and maintainers

## Summary

The emulator's frame loop no longer allocates in steady state. One minute of a real
Kickstart boot previously allocated 978 521 times; it now allocates nothing, and a test
enforces it.

## User And Operator Impact

Two buffers were rebuilt on every scanline. The copper's pending register writes cost one
allocation per frame on a small copper list. The guest register writes drained from the
memory log cost roughly one per scanline during a real boot, because a booting guest writes
custom registers on nearly every line.

On the ESP32-P4 target this matters before capacity does: a steady allocation rate in the
frame loop is a latency and fragmentation problem, and 32 MiB of PSRAM does not make it one
that can be ignored.

Emulated behaviour is unchanged. The state digest after 3605 frames of a real boot is
identical before and after, and the 1200-frame A1200 capture keeps its recorded digest.

## Compatibility And Migration

`Emulator` gains `guest_reg_writes_capacity`, `copper_writes_capacity`, and
`early_video_scanlines_capacity`. They exist for measurement: a total allocation count says
something allocated, while a capacity that stops growing names the buffer. Unlike a global
allocator hook they work in the `no_std` profile and on a device.

`rumiga-core` gains a `stats_alloc` dev-dependency, pinned at `=0.1.10`. It is a test-only
dependency and does not enter any shipped binary. The workspace sets
`unsafe_code = "forbid"`, which a counting `#[global_allocator]` cannot satisfy, so the
wrapper comes from outside the workspace rather than being written here.

## Verification

`cargo +1.97.1 test --locked -p rumiga-core --test allocation_test` runs 64 frames with the
copper active and a guest 68k loop writing a colour register, then asserts zero allocations
and zero reallocations. It lives in its own test binary, because a global allocator counts
every thread in the process.

Locally, against Kickstart 46.143, one minute of PAL is 3005 frames and allocates nothing.
The same measurement before the fix reports 978 521 allocations and 3 949 644 bytes.

Reverting either fix fails the test. Reverting the guest register write buffer reports
658 944 allocations over 64 frames.

## Known Limitations

The one-minute measurement cannot run in CI, because ROMs are not committed. CI enforces
the 64-frame test; the one-minute figure is recorded from a local run.

The measurement covers the core's frame loop only. The desktop shell allocates per frame in
its presentation and screenshot paths, which is not measured and not claimed; the shell is
not the loop the device runs.

This counts allocation calls, not footprint. Peak resident memory is a separate question.

The retained buffers grow on demand and never shrink. Both are bounded by what one scanline
can produce, and the measurement shows them settling at 64 and 32 entries, but nothing
enforces a cap.
