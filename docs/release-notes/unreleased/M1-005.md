# M1-005: Deterministic Single-Owner Blitter

- Status: Unreleased
- Change type: Fixed
- Task: M1-005
- Audience: Embedded integrators and maintainers

## Summary

The blitter no longer runs on a background thread. Both runtime profiles execute
the blit in place under one owner, and a new state digest proves that they reach
the same machine state.

## User And Operator Impact

Three defects disappear with the thread.

The blitter interrupt is now raised when the blit completes. Previously it was
raised only by a later synchronisation, which meant the portable profile never
raised it at all, so guest code waiting on the blitter interrupt would wait
forever on a device.

The guest-visible BBUSY bit in `DMACONR` no longer reports whether a host thread
handle exists. Host scheduling was observable through the standard blitter-wait
idiom.

A state or memory diagnostic taken during a blit no longer reads an empty chip RAM
slice, because the emulator keeps its memory throughout.

Desktop frame output is unchanged. A 60-frame Kickstart 46.143 capture is
byte-identical to the same capture from the previous implementation.

## Compatibility And Migration

`Emulator::sync_blitter` and `Emulator::sync_blitter_lazy` are removed, together
with the `AmigaMemory` thread fields and their sync methods. No replacement is
needed: a blit result is visible to the next access.

A blit takes no emulated time, so `DMACONR` BBUSY always reads clear and a guest
`WaitBlit()` loop exits immediately. Cycle-accurate blitter timing is separate
future work.

`core_affinity` leaves the workspace. It was used only by the blitter path, and
the desktop crate declared it without using it.

## Verification

`cargo +1.97.1 test --locked -p rumiga-core --lib` passes under both explicit
runtime profiles. Four blitter tests fail on the previous implementation and pass
now: repeated runs agree, completion requests the interrupt, BBUSY reads clear,
and the digest distinguishes distinct machine states. A pinned fixture digest is
asserted in both profiles, so the desktop and portable paths cannot diverge
silently.

On the host, three consecutive 60-frame captures are byte-identical to each other
and to the same capture taken from the threaded implementation.

## Known Limitations

Frame time was not measured. The thread presumably existed for throughput, so the
cost of removing it is the real open question and belongs to the M9 performance
work. Correctness is shown; speed is not.

The new digest is a 64-bit FNV-1a value for equality comparison only. It is not
cryptographic and must not be used for integrity or authenticity claims.
