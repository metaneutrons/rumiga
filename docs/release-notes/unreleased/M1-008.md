# M1-008: Bounded Queues And Overflow Policy

- Status: Unreleased
- Change type: Added
- Task: M1-008
- Audience: Embedded integrators and maintainers

## Summary

Queues now state their capacity, name their overflow policy, and count what they lose. The
guest keyboard queue adopts the contract, so a dropped keystroke is recorded instead of
vanishing.

## User And Operator Impact

Lost keystrokes were previously invisible. The keyboard queue held sixteen events behind an
unnamed length check, and past that the event was skipped with nothing recorded. The queue
drains about seventeen events per second under PAL, so a key-repeat burst exceeds it in
normal use, and a guest that missed a keystroke looked exactly like one that received
everything.

The shell now reports saturation. If events were lost it prints how many and the peak
depth; if the queue reached its limit without losing anything it says so, because a full
queue that held is worth knowing about.

Capture manifests gain an `input_queue` section with the capacity, the policy, and the
depth, high-water, and dropped counters. In a capture run these read zero, which documents
that no input pressure could have influenced the frame.

Guest-visible behaviour is unchanged. The keyboard queue keeps the same capacity and the
same overflow behaviour it already had; only the naming and the counting are new. A
1200-frame A1200 capture keeps the digest recorded for M1-013 and M1-007.

## Compatibility And Migration

`rumiga-platform` gains `BoundedQueue<T>`, `OverflowPolicy`, and `QueueAdmission`.

`OverflowPolicy::RejectNewest` keeps the backlog and loses the incoming item.
`OverflowPolicy::DropOldest` evicts the head to make room. Choose per queue: keyboard input
wants the first, audio wants the second.

`QueueAdmission` distinguishes three outcomes rather than two, because eviction both
queues the new item and loses an old one. `queued()` and `lost_an_item()` answer those
questions separately.

`BoundedQueue::clear` keeps `high_water` and `dropped`. They describe the queue's history,
so a reset would hide a saturation episode.

`Emulator::key_event` returns `QueueAdmission` instead of `()`. Existing callers compile
unchanged; a caller that wants per-event detail can now have it, and the aggregate is
available through `key_queue_depth`, `key_queue_high_water`, `key_queue_capacity`,
`key_events_dropped`, and `key_queue_policy`.

`InputCapabilities` gains `max_events_per_poll`. `InputState::key_events` is an unbounded
`Vec`, so this is the bound a consumer sizes against. Code constructing
`InputCapabilities` literally must add the field; `Default` reports zero.

## Verification

Both policies are tested, including a case where they disagree about which item survives,
which is the reason the policy is named per queue at all. The admission outcomes, the
high-water mark surviving a drain, the counters surviving `clear`, and a zero-capacity
queue losing everything under either policy are covered.

The real consumer is tested rather than only the type. Filling the keyboard queue to
capacity and pushing once more returns `Rejected`, the dropped counter reads one, the
event that was already at the head is still there, and the high-water mark outlives a full
drain. This holds in both runtime profiles.

## Known Limitations

No audio or video queue is created. `AudioOutput` and `Storage` still have no backend, so a
queue for them would have neither producer nor consumer and could not be tested against
real pressure. The bound that `AudioCapabilities::max_queued_frames` declares therefore
still describes an intention rather than an enforced limit.

The counters are cumulative and never reset. There is no windowed rate, so a shell cannot
distinguish a burst that happened an hour ago from one happening now. Telemetry with time
windows is later work.

The keyboard queue's three-frame drain interval is unchanged. Its capacity is the reason
bursts are lost; a deeper queue or a faster drain is a separate question that this change
only makes measurable.
