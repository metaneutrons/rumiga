# M1-012: Published Portability Contract

- Status: Unreleased
- Change type: Added
- Task: M1-012
- Audience: Embedded integrators and maintainers

## Summary

The portability contract is published in one place with its enforcement named per rule, and
the core dependency graph is now closed: exactly three workspace crates and no third-party
dependency, checked by the portable gate.

## User And Operator Impact

Nothing changes for a user. An integrator can now read the whole contract as a table in
`ARCHITECTURE.md`, with each rule naming the gate, lint, or assertion that enforces it and
the task it arrived with.

Pulling any external crate into the core now fails the portable gate. Previously the
supply-chain gate held licences, registries, sources, and advisories, and the portable gate
compiled the core for the bare-metal target, but nothing constrained which crates could
appear in the core graph.

## Compatibility And Migration

`toolchain/manifest.toml` gains `[portable_rust.core_graph]` declaring the profile, the root
package, and the closed crate set. Adding a dependency to the core requires editing that
section and the firmware manifest test that pins it, which is a reviewed change rather than
a side effect.

The gate compares normal edges only. Build and dev dependencies do not ship in the core, so
the `stats_alloc` dev-dependency added by M1-010 is outside the set by design.

No public API changes.

## Verification

Both directions of the comparison are probe-verified. Removing `rumiga-platform` from the
declaration produced `portable core graph contains crates the manifest does not permit`.
Adding a crate the graph does not contain produced `portable core graph no longer contains
declared crates`. Both probes touched only the manifest, so no dependency or lockfile was
disturbed.

The firmware manifest test pins the declaration's profile, root, and exact crate list, so
widening the set fails in two places rather than one.

The published table was checked row by row against the enforcement each row names.

## Verified Promotion

Pull-request run `32178866587` and final `main` run `32179481741` passed all required jobs.
The portable job executed the graph comparison in CI and both host legs pinned the
declaration, so the closed set resolves the same way there as on the development host.

Both governance artifacts were checksum verified with two independent implementations against
the artifact's own `SHA256SUMS`, and the final manifest's recorded input digests match the git
tree at the promoted revision.

## Known Limitations

The closed set is stricter than the plan's wording, which asks for approved `no_std` crates.
That is deliberate: the core needs no third-party crate today, and "approved `no_std`" is not
a stable property across versions.

The lockfile gate is a partial defence rather than a substitute. A dependency added without a
lockfile update fails at `--locked` before the graph check runs; one committed together with
its lockfile update reaches the graph check, which is the case that motivates it.

The contract covers `rumiga-core` and what it pulls in. The desktop shell and the ESP
platform crate are outside it by design; the platform crate's own graph is covered by the
`foundation` portable profile rather than by the closed-set rule.

Two rules in the table are weaker than they read, and say so there: the pointer-width rules
are compile-time assertions evaluated for the target rather than tests executed at a 32-bit
`usize`, and the allocation rule is enforced over a 64-frame fixture in CI with the
one-minute figure measured locally, because ROM images are not committed.
