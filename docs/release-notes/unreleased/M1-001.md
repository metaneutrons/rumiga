# M1-001: Explicit Core Runtime Profiles

- Status: Unreleased
- Change type: Changed
- Task: M1-001
- Audience: Embedded integrators and maintainers

## Summary

`rumiga-core` now provides explicit, mutually exclusive `std` and `no_std`
features. `std` remains the default; the allocator-backed `no_std` profile
removes the core's direct host filesystem, thread, and CPU-affinity requirements.

## User And Operator Impact

Desktop behavior and commands are unchanged. Embedded integrations must select
`--no-default-features --features no_std` and provide a global allocator.
File-backed CPU tracing is available only in the default `std` profile, and the
current `no_std` blitter path executes synchronously.

## Compatibility And Migration

Existing desktop consumers require no migration. A dependency that disables
default features must now explicitly select `no_std`; selecting neither profile
or both profiles is rejected with a targeted compile error.

## Verification

The canonical host gate checks the explicit `std` profile, lints and tests the
complete core under `no_std`, rejects both invalid feature selections, and then
runs the normal workspace validation.

## Known Limitations

This change does not make the complete core dependency graph bare-metal
compatible. `m68k` still requires `std` and is converted by M1-002. Injected
trace services and deterministic single-owner blitter execution remain M1-004
and M1-005.
