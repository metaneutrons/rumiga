# M1-009: Deterministic Input Replay

- Status: Unreleased
- Change type: Added
- Task: M1-009
- Audience: Users, embedded integrators, and maintainers

## Summary

Input can be recorded against emulated frames and replayed. The same recording reaches the
same machine state on every run, and the state digest was widened so that claim means
something.

## User And Operator Impact

`--record-input PATH` writes every key, pointer motion, and button change with the emulated
frame it happened on. `--replay-input PATH` plays a recording back. The two are mutually
exclusive: recording a replay would copy the input file back out while claiming to have
observed it.

The recording format is text with a version header, so a scenario can be written by hand,
read in a review, and diffed against another. A malformed file is refused before the machine
starts, with a message naming the line.

Capture manifests gain a `replay` section with the frame count, the number of replayed
events, the recording's digest, and whether replay is exhausted, plus a `digests` section
with the state, frame, and media digests. Recorded evidence therefore names the input that
produced it.

Rendered output is unchanged. A 1200-frame A1200 capture keeps the digest recorded since
M1-013.

## Compatibility And Migration

`rumiga-core` gains a `replay` module with `InputEvent`, `RecordedInput`, `InputRecording`,
`InputRecorder`, and `ReplayError`.

`Emulator` gains `frames_run`, `start_input_recording`, `finish_input_recording`,
`is_recording_input`, `attach_input_replay`, `replayed_recording`, `replay_exhausted`, and
`media_digest`. `run_frame` now applies the current frame's replayed events before running,
so a shell must not apply them itself.

`Emulator::state_digest` covers considerably more: the frame counter, the keyboard queue's
contents and dropped count, the mouse deltas, counters and buttons, both CIA chips, slow and
fast RAM, and per-drive metadata. Digests recorded before this change no longer compare.
Media contents are no longer implicitly excluded by omission but explicitly separate, in
`media_digest`.

`AmigaMemory` gains `slow_ram_bytes` and `fast_ram_bytes`. `CiaState` gains `write_digest`.
`BoundedQueue` gains `iter`, so a digest can see pending items without draining them.

## Verification

The format round trip, every rejection case with its line number, and the recorder's
suppression of unchanged button state and zero deltas are covered.

Replay is verified four ways: the same recording reaches the same digest twice, a recording
differing in one keycode reaches a different digest, each event lands on its own frame, and a
recorded session replays to the digest it was captured from, through the text form. All of it
holds in both runtime profiles.

On the host, three replays of a hand-written scenario reach the same state digest while the
same run with no input reaches a different one. All four runs share the same frame digest,
because the Kickstart insert-disk screen does not react to those inputs. That is why the state
digest exists: comparing screenshots would have shown no difference and proved nothing.

## Known Limitations

Replay determinism assumes the network is disabled, which is the default. The SLIRP backend
injects host-received Ethernet frames into the machine and those are not recorded, so a
replay with networking enabled will not reproduce.

Replay also assumes the same media. A recording carries no reference to the ROM or disk images
it was made against, so replaying it on a different disk is silently a different session. The
manifest records the media digest, which lets a reader notice this after the fact.

The state digest still does not cover the copper and blitter shadows beyond `custom_regs`, the
audio channel state, the floppy MFM track buffers, or the IDE transfer state.

A recording must be attached before any frame runs. Events whose frame has already passed are
never applied, and nothing warns about it.

There is no windowed or partial replay: a recording plays from frame zero to its end.
