# M2-003: Declared Boot Policy

- Status: Unreleased
- Change type: Added
- Task: M2-003
- Audience: Embedded integrators and maintainers

## Summary

The PSRAM allocator, panic, core-dump, watchdog, logging, and reset policy is declared in one
place and checked from both sides. Core dumps now go to the flash partition that was already
reserved for them, a task watchdog timeout now reboots, and the boot manifest reports the
policy alongside what the running system actually has.

## User And Operator Impact

A panic on a device leaves a checksummed core dump in encrypted flash rather than nothing.
The partition was reserved by M2-013 and core dumps were switched off, so the space was spent
and unused.

A hung task now reboots the device instead of logging a warning and staying hung.

Field diagnosis can be raised to DEBUG at runtime without a new image. The default stays
INFO.

The application grew from 182,512 to 204,400 bytes, which is 3.25% of a 6 MiB slot.

## Compatibility And Migration

`toolchain/manifest.toml` gains a `[boot_policy]` section with five subtables. It is the one
place these values are written, and the firmware gate fails if the built image disagrees.

`firmware/partitions.csv` marks `coredump` as `encrypted`. Offsets and sizes are unchanged,
so no application slot moves, but the partition table binary differs and a device would need
the new table.

`rumiga.firmware.build.v1` gains an additive `boot_policy` section, following the practice
M0-014 set for `merged_image`. Its `reset_reason` is `null`, because that value only exists
at runtime.

`rumiga-platform-esp` gains a `boot` module with `BootManifest`, `BootObservations`,
`ResetReason`, and the policy constants, plus a `toml` dev-dependency for the pinning test.

The partition-layout comparison now includes the `encrypted` flag and rejects an unrecognized
flag. A layout that relied on a misspelled flag being ignored will now fail.

## Verification

The firmware gate compares the declaration against the resolved `sdkconfig` for every value,
and cross-checks two things that span files: that the core-dump partition is marked encrypted
whenever flash encryption is on, and that whole-DRAM capture is not declared against a
partition smaller than the 128 KiB ESP-IDF documents.

Four probes made the new checks fail before they were trusted. Removing `encrypted` from the
`coredump` row was rejected with a message naming the plaintext consequence. Declaring
whole-DRAM capture was rejected with "needs at least 131072 bytes reserved and the coredump
partition is 110592 bytes". Declaring a 9 second watchdog period against a build configured
for 5 was rejected. Changing a mirrored constant failed the pinning test. All four were
reverted and each reversion verified by search.

Ten host tests cover the mirror against the declaration, that a watchdog reset is
distinguishable from a panic, that ordinary starts are not counted as faults, that reset
reason names are distinct, that the rendering reports policy and observation separately, and
that the `encrypted` flag survives the CSV parser, is read from the binary table, is rejected
when misspelled, and shows as a difference when one side lacks it.

## Known Limitations

Nothing has booted. The boot manifest is a type with a rendering and an ESP-IDF reader,
compiled by the firmware and portable gates but never executed on a device.
`firmware/src/main.rs` is still a stub, so nothing emits the manifest yet, and the reset
reason is recorded as absent rather than measured.

The watchdog decision carries an obligation that nothing enforces. The emulator frame loop
will run hot, and a task that monopolizes a core without yielding starves that core's idle
task and trips a watchdog that now reboots. The loop must yield or subscribe itself and feed
the watchdog. Today there is no loop, so there is nothing to check.

Whole-DRAM core dumps are out for the life of this layout. The partition is 108 KiB against a
documented 128 KiB minimum, and enlarging it would move the application slots, which an OTA
image cannot survive on a device already flashed with the old table.

The policy values are written twice, in the manifest and as Rust constants, because integer
`sdkconfig` values do not reach Rust as cfgs. A test pins the two together; it does not
remove the duplication.

The observed values in the manifest are PSRAM and internal free memory. Nothing yet reports
clock frequencies, cache configuration, or partition state.
