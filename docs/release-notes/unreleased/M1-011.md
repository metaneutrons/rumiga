# M1-011: Portability Boundaries

- Status: Unreleased
- Change type: Added
- Task: M1-011
- Audience: Embedded integrators and maintainers

## Summary

The two assumptions that separate the 64-bit development hosts from the 32-bit device are
now enforced rather than implicit: guest values must be converted with an explicit byte
order, and `usize` must be wide enough to hold a guest address.

## User And Operator Impact

Nothing changes for a user. This closes two ways a future change could produce a core that
passes every host test and behaves wrongly on the device.

A native-endian conversion is now rejected at lint time. The Amiga is big-endian while the
hosts and the RISC-V target are little-endian, so `from_ne_bytes` would read guest values
with the wrong byte order. The workspace already contained none, with 35 explicit
big-endian conversions; the ban keeps it that way.

A build for a target where `usize` is narrower than a guest address now fails with a
message naming the reason, instead of truncating every address silently.

## Compatibility And Migration

`crates/rumiga-core/clippy.toml` gains `disallowed-methods` entries for `from_ne_bytes`
and `to_ne_bytes` on the integer types, and `lib.rs` denies
`clippy::disallowed_methods`. Code in the core that needs a byte conversion must state
`from_be_bytes` or `to_be_bytes`. Nothing in the crate needed changing.

`lib.rs` gains two compile-time assertions: `usize` is at least as wide as `u32`, and a
chip RAM length fits in `u32`. Both hold on every supported target.

No public API changes.

## Verification

Seven property fixtures cover the boundaries: a guest address survives conversion through
`usize` across the whole 32-bit range including its edges, word and long access through the
CPU's own bus is big-endian in both directions with individual bytes checked rather than
only the round trip, every modelled RAM length fits in `u32`, and the framebuffer index
space fits in 32 bits.

Both invariants were verified against probes rather than assumed. A temporary
`u32::from_ne_bytes` was rejected with `use of a disallowed method`. A temporary assertion
requiring a 128-bit `usize` failed the build with its own message. Both probes were
removed and the tree re-checked.

## Known Limitations

Miri is not used, and this is deliberate rather than deferred. Miri detects undefined
behaviour, the workspace forbids unsafe code, and neither silent truncation nor a wrong
byte order is undefined. A Miri leg would look like coverage while detecting neither
failure mode.

The pointer-width claim rests on compile-time assertions and the existing `riscv32imafc`
compile gate, not on execution with a 32-bit `usize`. No such target with a usable `std`
exists on the development host, and an `i686` leg would exercise a width the product never
runs.

Alignment is not separately instrumented. The core stores guest memory as byte slices and
composes wider values from bytes, so it makes no alignment assumption to violate. That is a
property of the design rather than something enforced here.

The ban applies to `rumiga-core`. The desktop shell's own conversions are outside it.
